## 아직 안 된 것

### MongoDB

MongoDB 컨테이너를 시작하려 했으나 호스트의 `127.0.0.1:27017` 포트를 다른 프로세스가 사용 중이라 시작하지 못했다.

오류:

```text
Bind for 127.0.0.1:27017 failed:
Only one usage of each socket address is normally permitted.
```

생성된 MongoDB 컨테이너는 현재 `Created` 상태일 수 있다. 먼저 기존 27017 사용 주체를 확인해야 한다.

### Spark

`pipeline/` 코드는 존재하지만 아직 다음 단계는 실제 검증하지 못했다.

```text
Kafka → Spark → MongoDB
```

현재 Spark 코드는 Kafka 원본 레코드를 `raw_events`에 적재하는 기본 파이프라인에 가깝다. JSON 정제, 중복 제거, quarantine, 집계, 대시보드 연동은 다음 작업이다.

### QA 대시보드

QA 대시보드 화면은 실행되지만 실제 시스템 MongoDB 조회는 아직 TODO다.

관련 파일:

- `qa/src/ticket_guard_qa/system_targets/live_mongo_reader.py`
- `qa/src/ticket_guard_qa/dashboard/routes/db_dashboard_routes.py`

## 내일 첫 작업 순서

### 1. 작업 디렉터리와 컨테이너 상태 확인

```powershell
cd C:\workspace\Ticket_Guard
git status --short --branch
docker compose -f compose.yml -f compose.gateway.yml ps -a
docker network ls
```

### 2. 27017 포트 사용 주체 확인

```powershell
Get-NetTCPConnection -LocalPort 27017 -State Listen |
  Select-Object LocalAddress,LocalPort,OwningProcess

Get-Process -Id <OwningProcess>
```

기존 MongoDB가 실제 프로젝트용이면 재사용 가능성을 확인한다. 정체를 모르는 프로세스를 바로 종료하지 않는다.

### 3. MongoDB 시작 또는 포트 충돌 해결

MongoDB를 사용할 수 있게 된 뒤 다음 명령으로 시작한다.

```powershell
docker compose -p ticket-guard-workspace-db --profile mongo `
  -f compose.yml -f mongo/compose.local.yml up -d mongo

docker compose -p ticket-guard-workspace-db `
  -f compose.yml -f mongo/compose.local.yml ps -a
```

주의: `mongo/compose.local.yml`만 단독으로 사용하면 image/build 정보가 없어 실패한다. 반드시 `compose.yml`과 함께 사용한다.

### 4. MongoDB 네트워크와 계정 확인

`.env`의 다음 값이 MongoDB 초기화 값과 일치해야 한다.

```env
MONGO_ROOT_USERNAME=...
MONGO_ROOT_PASSWORD=...
MONGO_WRITER_USERNAME=...
MONGO_WRITER_PASSWORD=...
MONGO_DATABASE=ticketguard
```

Spark는 기본적으로 다음 호스트를 사용한다.

```env
SPARK_MONGO_HOST=ticket-guard-workspace-db-mongo-1
SPARK_MONGO_PORT=27017
SPARK_MONGO_NETWORK=ticket-guard-workspace-db_mongo-backend
```

### 5. Spark 환경 점검

MongoDB가 정상화되면 먼저 실제 이벤트를 처리하지 않는 `check`를 실행한다.

```powershell
docker compose --profile spark run --rm spark check
```

통과해야 하는 항목:

- Spark 실행
- Kafka connector 로딩
- Kafka topic 조회
- MongoDB DNS 연결
- MongoDB 인증
- writer 권한
- `raw_events` 확인
- checkpoint 쓰기 권한

### 6. Spark 원본 적재 실행

환경 점검이 통과하면 실행한다.

```powershell
docker compose --profile spark up -d --build spark
docker compose logs -f spark
```

확인할 로그:

```text
pipeline ready mode=ingest
pipeline ingest_started
pipeline batch_start
pipeline batch_saved
```

## 다음 구현 순서

### 1차 목표: Kafka → Spark → MongoDB raw_events

먼저 이것만 완료한다.

```text
Django 이벤트
  → Kafka ticketguard.events.v1
  → Spark Structured Streaming
  → MongoDB raw_events
```

### 2차 목표: 이벤트 정제

다음 컬렉션을 추가한다.

- `clean_events`: JSON 파싱 및 계약 검증을 통과한 이벤트
- `quarantine_events`: 잘못된 이벤트와 실패 사유

반드시 포함할 정책:

- UTF-8/JSON 파싱
- 필수 필드 검사
- `schemaVersion` 검사
- UTC 시간 정규화
- `eventId` 기준 의미 중복 제거
- 민감정보를 quarantine에 저장하지 않기

### 3차 목표: 대시보드용 집계

`event_metrics` 컬렉션을 추가한다.

최소 지표:

- 전체 이벤트 수
- 이벤트 타입별 수
- 예매 성공/실패 수
- 성공률
- 평균 처리 시간
- p95 처리 시간
- 중복 이벤트 수
- quarantine 이벤트 수
- Kafka → Spark → MongoDB 지연

### 4차 목표: QA 대시보드 연결

QA는 시스템 MongoDB에 쓰지 않고 read-only 계정으로 읽기만 해야 한다.

구현 대상:

- `qa/src/ticket_guard_qa/system_targets/live_mongo_reader.py`
- `qa/src/ticket_guard_qa/dashboard/routes/db_dashboard_routes.py`

처음에는 `/qa/db` 화면에 다음만 표시한다.

- 최근 이벤트 수
- 최근 집계
- quarantine 수
- 마지막 Spark 처리 시각
- pipeline 지연

## 내일 절대 먼저 하지 말 것

- 바로 대시보드 화면부터 꾸미지 않기
- `raw_events`를 정제 데이터처럼 사용하지 않기
- `eventId` 중복 정책 없이 aggregate부터 만들지 않기
- MongoDB 포트 충돌 원인을 모른 채 기존 프로세스를 강제 종료하지 않기
- `docker compose down -v` 사용하지 않기. Kafka/MongoDB 데이터 볼륨이 삭제될 수 있음

## 핵심 상태 한 문장

현재는 “Django가 만든 예매 이벤트가 Kafka에 실제로 들어가는 것”까지 성공했다. 내일은 MongoDB 연결을 해결하고 `spark check`를 통과시킨 다음, Kafka 원본 이벤트가 MongoDB `raw_events`에 저장되는 것을 확인하면 된다.
