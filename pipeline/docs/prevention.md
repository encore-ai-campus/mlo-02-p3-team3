# 서버 사전 제한과 단계별 탐지 현황

## 구현 범위

웹 서버가 요청 처리 중 다섯 정책을 판정한다. Spark 응답은 기다리지 않는다.
각 제한은 300초이며 제한 중 요청 거절로 만료 시각을 갱신하지 않는다.
기존 브라우저 쿠키 로그인 보호, 보안문자, 단계·페이지·순서 검증은 유지한다.
기존 확정 요청 과다(3초 10회) 규칙은 계속 관찰 전용이다.

|지표|범위|기준|화면 단위|
|---|---|---|---|
|반복 로그인 실패|계정, 실제/시뮬레이션 분리|시간창 없는 누적 5회, 성공 시만 초기화|탐지 건|
|오픈 전 반복 요청|계정·공연·회차·자료 구분|직전 2초 시작 API의 NOT_OPEN 10회|탐지 건|
|반복 재입장|계정·공연·회차·자료 구분|직전 2초 새로운 시도 10개|탐지 건|
|반복된 잘못된 선택|예매 시도, 제한은 계정·공연·회차|직전 5초 대상 오류 10회|탐지 건|
|구매 한도 초과 시도|계정·공연·회차·자료 구분 전체|유효 구매량 + 요청량 > 4매|탐지 건|

시간창은 양 끝을 포함한다. N번째부터 탐지한다. 한 번 제한된 동안에는
추가 탐지/적용을 만들지 않고 `prevention_rejected`만 별도로 기록한다.
만료 뒤 새 위반으로 다시 제한될 수 있다. 로그인 실패 누적은 만료로 지우지 않는다.
로그인 제한 도달 카드는 새 정책 자료에서 실제 제한 적용 수를 나타낸다.
과거 브라우저 잠금 사건만 있는 범위는 기존 집계를 보존한다.
지표는 중복 대상이 있어 서로 합산하지 않는다.

## 이벤트와 원본 흐름

`web/prevention.py` / `web/prevention_store.py`
→ 트랜잭션 outbox → 기존 EventDispatcher → 기존 Kafka topic
→ 기존 Raw Consumer의 `unclassified_events` (라우팅 v1 및 그룹 유지)
→ Spark flow 모드의 원본 바이트 대조
→ `early_observations` 허용 필드 투영
→ `server_policies` 정책·버전·범위·적용 근거 검증
→ `stageDetections` / `early_detections` / `early_actions`
→ 검증된 `early_versions` → 마지막에 `early_public` 포인터 교체
→ 관리자 전용 리더 → 기존 네 단계 그래프와 공통 상세.

`prevention_evaluated`, `prevention_detected`, `prevention_applied`,
`prevention_rejected`, `prevention_released`를 구분한다.
원본 이벤트 ID는 발행 재시도에 유지한다. 요청 ID는 실제 서버 수신 요청마다 새로
생성하고, 예매 시도 ID는 한 번 생성한 시도의 수명 동안 유지한다.
제한 ID는 탐지·적용·제한 중 거절·해제를 연결한다.
탐지는 제한 ID별 1건, 적용은 제한 ID별 1건, 제한 중 거절은 요청 ID별 1건이다.
동일 제한 ID의 모순된 대상·관측값·근거는 공개하지 않는다.

정책 버전은 `prevention-2026-11-23-v1`이다. 기존 관찰 전용 정책의 버전/활성
설정은 바꾸지 않는다. 새 정책 정보는 각 지표에 별도로 공개한다.
새 이벤트로 기존 사용자 흐름의 접속·체류 활동 시각을 바꾸지 않는다.
인증정보·요청 본문은 정책 저장소와 새 관측 컬렉션에 복제하지 않는다.
실제/시뮬레이션/구분 미확인 공개 범위는 기존 방식으로 분리한다.
설정된 QA 계정은 서버가 식별하며 새 정책 및 해당 계정의 예매 이벤트를 시뮬레이션으로
표시한다. 클라이언트의 임의 시뮬레이션 주장으로 정책 범위를 바꾸지 않는다.

## 영속 상태 및 구매 원장

기존 구매 원장은 메모리뿐이어서 웹 전용 SQLite 파일을 추가했다. Django ORM,
세션 DB나 QA DB를 도입하거나 교체하지 않는다. 표준 라이브러리만 사용한다.
`TICKETING_STATE_PATH`의 기본값은 프로젝트 루트의
`.ticketguard-state/web.sqlite3`다. 로컬 개발의 기존 `/app` 바인드 마운트에서는
파일이 보존된다. compose 웹 서비스는 별도 `web-policy-data` 볼륨을
`/var/lib/ticketguard`에 연결하고 해당 경로의 `web.sqlite3`를 사용하도록 구성했다.
볼륨은 이번 작업에서 생성하지 않았다. Git과 이미지 빌드에서는 로컬 상태 디렉터리를 제외한다.

운영 전 반드시 웹 프로세스들이 공유하는 **영속 로컬 파일 경로**를 지정하고
백업/복구와 디스크 용량을 검증해야 한다. 서로 다른 호스트에 별도 파일을 만들어
수평 확장하는 구성은 지원하지 않는다. 네트워크 파일시스템을 사용하지 않는다.
파일을 삭제·초기화하면 누적 한도가 사라지므로 운영 중 초기화하면 안 된다.
compose 프로젝트/볼륨 이름을 변경해 빈 원장을 만드는 일도 피해야 한다.
기존 QA reset이나 `MockRepository.reset()`은 이 원장을 지우지 않는다.

하나의 `BEGIN IMMEDIATE` 트랜잭션에서 누적량 확인·새 구매 기록·구매 성공 이벤트
outbox를 저장한다. 시도 ID는 유일하고 구매 ID도 유일하다. 동일 시도의 확정은
재시작 후에도 저장된 계정·페이지·회차 정보를 확인한 뒤 기존 결과를 재응답한다.
새 재고 차감이나 구매량 증가가 없다. 저장소 오류는 503으로 거절한다.
시도·대기열·보안문자·재고 전체를 영속 저장소로 교체한 것은 아니다.
따라서 이 변경이 분산 재고/좌석의 동시 판매 문제까지 해결하지는 않는다.

현재 서버 카탈로그는 공연당 `show_id-evening` 하나의 회차만 제공한다.
요청의 임의 회차나 날짜를 조합하지 않고 이 서버 정의를 사용하며 구매 원장에도
회차를 고정한다. 동일 공연에 새 날짜/회차를 추가할 때에는 새 회차 ID가 필요하다.
기존 구매 전체를 백필하지 않았다. 새 원장은 이 코드 활성화 후의 구매만 보장한다.
이전 구매가 있는 운영 회차에 곧바로 적용하면 전체 누적을 보장할 수 없으므로,
적용 전 신규 회차 여부 또는 별도로 승인된 원장 전환 방안을 확인해야 한다.

확정된 취소/환불 연동 계약은 `Session.release(adjustment_id, booking_id, delta, kind)`다.
`kind`는 `cancelled` 또는 `refunded`이며 신뢰할 수 있는 서버 확정 처리만 호출한다.
동일 확정 ID는 멱등 처리하고, 다른 내용으로 재사용하면 오류다. delta는 새로
해제되는 수량이다. 취소 뒤 그 수량의 환불을 중복 차감하면 안 된다. 원래 구매량보다
많이 해제하거나 알 수 없는 구매를 변경할 수 없다. 대기열 취소는 이 계약을 호출하지
않는다. 현재 제품에 결제/구매 취소/환불 확정 처리 자체가 없으므로 외부 확정 자료의
자동 연동은 수행하지 않았다. 없는 자료를 가정한 차감도 하지 않는다.

## 원인 연결과 해제

재입장은 서버가 생성한 시도 ID만 센다. 사용자 취소 뒤 생성은 포함하고 연결
만료 뒤 복구는 제외한다. 이전 시도 ID와 서버가 확인한 원인을 관측에 보존한다.
재시작 등으로 이전 상태의 원인이 불명확하면 `unconfirmed`로 남기고 계산에서
제외한다. 다른 공연·회차·자료 구분의 이전 시도는 결합하지 않는다.

선택 오류는 quantity_range / duplicate_seat / invalid_seat만 센다.
SEAT_SOLD와 INSUFFICIENT_STOCK은 제외되며 통신·서버 오류를 실패 횟수에 넣지 않는다.
기존 오류 코드는 보존한다. 요청량 자체가 4매를 넘으면 기존 선택 오류 응답과 함께
독립적인 구매 한도 초과 탐지/제한도 기록한다.

오픈 전 제한은 서버의 오픈 상태가 확인되는 다음 업무 요청에서 누적과 해당 제한만
해제한다. 다른 규칙 제한은 유지한다. 기존 데모 오픈 시각/시나리오 상태는 메모리다.
실제 운영 스케줄 저장소나 전역 개방 스케줄러를 새로 만든 것은 아니다.
만료도 시각 비교로 즉시 판정하며 해제 이벤트는 다음 요청 때 기록한다.
화면은 명시적 종료 시각으로 만료와 미확인을 구분한다.

## 집계·게시·처리량

최근 2시간 판정 갱신, 300초 지연 비교 보조 범위와 최근 1시간 표시를 유지한다.
서버 결정은 평생 구매 원장이나 로그인 전체 누적을 Spark의 2시간 자료로 추측해
재판정하지 않는다. 지연 도착한 적용/해제 근거는 다음 버전의 상세에 연결한다.
적용 근거가 없으면 조치 수는 `null`/`—`이며 미조치로 단정하지 않는다.
신규 정책 평가 근거가 없는 구버전/빈 범위도 0이 아닌 근거 부족이다.
카드 상세에는 탐지 수, 실제 조치 수, 제한 중 거절 수, 고유 제한 계정 수를 분리한다.

25,000개 관측 상한, 100개 범위, 공개 버전 8MiB, 상세 최근 200개 상한은 유지한다.
새 이벤트 증가로 상한에 더 빨리 도달할 수 있다. 초과 시 새 공개를 보류하고 이전
포인터를 보존하며 실패 상태를 표시한다. 처리량 벤치마크에 근거한 수치는 아니다.
웹 시간창 메모리는 규칙별 최대 10개이며 로그인 누적/원장/outbox는 디스크에 보존한다.
outbox 전송은 매 요청 뒤 최대 100개다. 장애 중에는 삭제하지 않으므로 디스크/지연
관측이 필요하다. 이벤트가 2시간 갱신 범위보다 늦게 복구되면 원본은 보존되지만
현재 화면 집계 범위에는 나타나지 않는다. 임의 장기 백필은 하지 않는다.

## 운영 적용 전 절차 (이번 작업에서 실행하지 않음)

1. 기존 회차 구매량 전환과 영속 경로·공유 범위·백업을 확인한다.
2. 웹 및 flow/관리자 이미지를 승인된 방식으로 적용한다. 자동 재배포하지 않는다.
3. 기존 Kafka/Raw Consumer와 Spark **flow 모드**가 가동되는지 확인한다.
   ingest 모드만으로는 early 공개 집계가 갱신되지 않는다.
4. 기존 관리자 MongoDB 읽기 권한과 flow 쓰기 권한의 early_* 접근을 확인한다.
   계정 생성/권한 확대를 이 구현에서 실행하지 않는다.
5. 기존 실행 체계에 `python manage.py drain_prevention_outbox`를 주기적으로 연결한다.
   요청이 끊겨도 Kafka 복구 후 발행을 재개하기 위한 절차다. 새 서비스/포트는 추가하지 않았다.
6. 실제 Kafka→원본 대조→MongoDB→관리자 연결, 만료·오픈 해제와 성능을 검증한다.

운영 DB 쓰기·백필·배포·계정 변경·커밋·푸시는 실행하지 않았다.

## 격리 회귀 검사

웹 기본 테스트 러너는 각 테스트에 임시 영속 파일을 배정한다. 테스트 내 재시작과
동시 요청은 같은 파일을 공유하며, 테스트 간에는 원장을 섞지 않는다. 운영 파일을
초기화하는 방식으로 격리하지 않는다. `python manage.py test web`으로 실행한다.
전체 연결 검사는 pipeline/admin 테스트 의존성과 두 소스 경로도 PYTHONPATH에 필요하다.
프로덕션 웹 의존성만 있는 환경에서는 해당 통합 검사 1개만 명시적으로 건너뛴다.

기존 로그인 테스트는 브라우저 보호의 monotonic 시계와 계정 영속 제한의 wall 시계를
함께 진행시켜 기존 429→200 검사를 유지했다. 브라우저 시간창이 지난 경우에도
기존 브라우저 실패 수 1과 새 계정 실패 수 5/실제 제한을 각각 확인하도록 강화했다.
QA 소유 테스트/리더는 수정하지 않았다.
