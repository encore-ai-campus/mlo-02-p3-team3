# 조기탐지·기존 사전 조치 관측

## 단계별 탐지 게시

일반 단계 요청·업무 사건 통계와 별도로 stageDetections에 규칙별 탐지 수를 게시한다.
로그인 제한, 중복 진행 위반, 보안문자 한도 도달, 단계 우회, 선택 조건 위반은
서버가 해당 사유로 판정한 사건만 센다. 로그인 실패·문제 변경 등의 전체 횟수를
반복 탐지 건수로 대체하지 않는다. 조치는 탐지 수와 별도 필드다.
보안문자 한도와 확정 요청 과다는 계정·예매 시도·범위로 고유 시도를 세며,
다른 서버 거절 규칙은 요청 ID+사유(없으면 사건 ID+사유)로 중복 제거한 관측 건수다.
고유 시도 식별이 불가하면 미확인 수를 따로 남긴다. 목록은 200개로 자르기 전에 전체 수를 계산한다.
관리자 사전 화면은 다섯 단계의 카드로 이를 게시하고 각 카드에서 대상과 근거를 펼친다.
기준 미정 규칙은 미구현, 조회 실패는 —, 구버전 자료에 새 집계가 없으면 집계 미반영이다.
기존 overlap/retry/pages 자료는 조회 범위가 같을 때만 연결한다. 사후 화면과 기존 규칙은 유지한다.

## 실행 경로와 경계

웹의 `ticketing_action_received` → Kafka → Raw Consumer 원본 보존 → Spark `flow` 원본 대조
→ `early_monitor` 최소 투영·집계 → 정합성 검사 → 불변 버전 저장 → 공개 포인터 → 관리자 조회다.
ingest의 기존 정제·격리·이상 판정과 network 모드는 바꾸지 않는다.
새 서버 수신 이벤트는 기존 사용자 흐름의 접속·체류 계산에 투입하지 않는다.
원본 검증은 기존 flow의 source/topic/partition/offset 및 바이트 대조를 재사용한다.
입력 바이트에서 독립적으로 투영을 재계산하고 일치할 때만 최소 관측을 저장한다.
기존 원본 라우팅 계약을 변경하지 않으므로 새 종류는 현재 unclassified_events에 원문 그대로 보존된다.
flow의 원본 대조는 이 컬렉션도 검색한다. 분류 변경은 별도의 버전 전환 작업이다.

서버의 새 UUID observationRequestId를 수신 사건과 해당 요청의 업무 사건에 부여한다.
브라우저의 요청 ID를 신뢰하거나 입력 본문·쿠키·토큰·정답을 새 관측에 복제하지 않는다.
계정의 서버 시도 ID가 요청 시도와 일치할 때만 서버의 공연·회차·시뮬레이션 구분을 연결한다.
나머지는 미확인 범위다. 로그인 전 계정·브라우저 고유 대상 수는 집계할 수 없다.
서버 회차 ID는 여전히 공연 ID + -evening이며 실제 다회차 정책은 별도 정리가 필요하다.
기존 업무 저장소는 단일 프로세스 메모리다. 재시작·다중 서버 간 제재 상태는 보장하지 않는다.

## 정책과 집계 단위

compose.flow.yml은 EARLY_MONITOR_ENABLED(기본 1), EARLY_MONITOR_SECONDS(기본 3),
EARLY_MONITOR_COUNT(기본 10)를 전달한다. 설정은 실행 시 검증하며 환경 파일을 자동 변경하지 않는다.
새 규칙은 항상 observe 모드다. 웹의 차단·취소·패널티 경로에서 이 결과를 읽지 않는다.
동일 계정·시도·공연·회차·시뮬레이션의 확정 요청 수신 사건을 대상으로 현재 요청 포함
직전 3초의 양 끝을 포함한다. 거절·재응답도 수신 요청에 포함한다.
같은 이벤트 재전달은 1회, 같은 사용자의 새 HTTP 요청은 새 서버 UUID로 별도 1회다.
기준을 만족하는 요청마다 1개 신호를 남긴다. 11개 요청이 모두 시간창 안에 있으면
10번째·11번째 요청에서 2개 신호, 고유 시도는 1개다. 에피소드 집계가 아니다.
동일 시각은 이벤트 ID 순서로 결정한다. 지연·역순 입력은 시간순 재계산하며 정책 버전별 이력을 유지한다.
기존 retry는 업무 수락 요청 사이의 시간 간격 규칙이다. 새 규칙과 합산하지 않는다.
heartbeat·재접속·페이지 새로고침·대기열 재입장은 이 규칙에 넣지 않는다.

단계 표는 수신 요청 수, 업무 사건 수, 식별 가능한 고유 시도·계정 수를 구분한다.
한 HTTP 요청에 여러 업무 사건이 발생할 수 있으므로 업무 사건 수는 요청 수와 같지 않다.
로그인 실패와 잠금 사건, 보안문자 오답과 한도 도달 사건은 분리한다.
시작 전 요청의 공연·회차 연결을 서버로 확인할 수 없으면 미확인 범위에 남긴다.
현재 대기 인원·코호트 전환율·전체 트래픽 완전성을 주장하지 않는다.
취소·만료는 대기열 이후에도 발생하므로 서버 요청 시작 단계가 queue로 확인될 때만
대기열의 취소·만료에 넣는다. 과거 자료 등 단계가 없는 사건은 별도 미확인 수로 표시한다.
관측이 없는 단계와 과거에 수신 이벤트가 없던 요청 수는 null이다.

조치는 기존 서버의 한도·상태·소유권·순서 검사 사건만 관측한다.
서버 요청 UUID + 사유로 중복을 제거한다. UUID가 없는 과거 사건은 조치 수에 임의 합산하지 않고
연결 근거 부족 사건 수에 표시한다. 종료 시각·해제·철회를 수집하지 않은 조치는 미관측이다.
로그인 기준값 등 수집하지 않은 정책값을 추정하지 않는다. 실제 조치와 과다 요청 신호는 별도다.

## 시간 통계와 보존

최근 1시간의 종료 관측을 기준으로 대기열 진입→입장, 입장→보안문자 성공,
보안문자 성공→첫 확정 수신, 확정 수신→구매 성공을 계산한다.
같은 계정·시도·공연·회차·시뮬레이션으로 한정하고 마지막 구간은 같은 서버 요청 UUID가 필수다.
누락·복수 선행 후보·역전·범위 미확인은 계산 불가다. 여러 요청 중 성공 요청을 추측하지 않는다.
평균·중앙값·nearest-rank p95와 표본 수·계산 불가 수를 게시한다.
새 빠른 완료 기준은 도입하지 않는다. 기존 anomaly의 fast 정책이 게시물에서 활성으로 확인되면
화면에 경고한다. 기존 ANOMALY_FAST_SECONDS와 정책 버전은 자동 변경하지 않는다.

계산·탐지 및 조치 이력 갱신은 최근 2시간과 300초 비교 유예를 읽고 화면은 최근 1시간이다.
관측의 expiresAt은 발생 시각 + 2시간 + 300초 + 1일이며 재소비로 연장하지 않는다.
탐지·조치 이력 보존 기간은 운영에서 별도로 결정해야 한다.
메모리 조회는 최대 25001개에서 중단하고 25000개 초과 시 공개를 실패시킨다.
25000은 기존 분석 상한과 같은 애플리케이션 안전 한도이며 부하로 검증된 처리량은 아니다.
공개 범위는 실제·시뮬레이션·미확인별 전체와 명확한 개별 공연·회차 조합을 분리한다.
전체 100개 범위, 버전 BSON 8MiB, 화면 목록 200개로 제한한다.
원본·본문을 메모리로 무제한 수집하지 않으며 기존 flow의 배치·상태 보존 제한도 적용된다.
현재 flow는 보존 범위 밖의 과거 업무 이벤트를 거부하므로 운영 과거 전체 백필 도구가 아니다.

## 저장과 공개

- early_observations: 원본 대조 완료 최소 필드·원본 위치·내용 fingerprint
- early_detections: 관찰 전용 규칙별 근거, 활성·철회 상태
- early_actions: 기존 서버 조치 근거와 연결 상태
- early_versions: 모든 범위의 카드·목록·시계열을 담은 불변 검증 버전
- early_public: 마지막에 교체하는 단일 공개 버전 포인터
- early_health: processing/ready/blocked 및 공개 버전·시각

정합성 검사는 단계 사건 합, 카드와 시계열 합, 규칙 버전, 범위, 문서 크기 및
같은 입력의 역순 재계산 일치를 확인한다. 배치 실패·부분 쓰기 중에는 새 버전을 공개하지 않는다.
타이머만으로 blocked를 해제하지 않고 원본 대조가 끝난 성공 배치 후에만 복구한다.
원본 대조는 전달 일치성을 검사하며 실제 봇 정답을 증명하지 않는다.
새 버전 전체 저장 후 포인터, health 순으로 게시한다. 여러 문서 쓰기는 트랜잭션이 아니다.
읽기는 health와 포인터를 앞뒤로 확인하고 해시·버전·시각·집계 계약을 검사한다.
120초를 초과한 자료나 blocked 자료는 기준 상태와 함께 수치 공개를 보류한다.
실패 시 고정 시안을 사용하지 않는다. 시안은 명시적 /admin/preview에서만 제공한다.
새 백필·정상 여부 필드·기존 clean 판정 변경은 없으며 운영 데이터에 쓰지 않았다.

## 운영 적용 전 절차

1. 웹과 pipeline 이미지를 검토·재빌드한다. 이번 작업에서는 배포하지 않는다.
2. 기존 flow의 원본 읽기 전용 연결·대상 DB·네트워크·체크포인트를 확인한다.
3. 지표 쓰기 계정의 새 컬렉션 쓰기·인덱스 권한을 확인한다.
4. 관리자 읽기 계정에 early_public/early_versions/early_health find가 필요하다.
   기존 계정·역할을 자동 확대하거나 비밀번호를 변경하지 않는다.
5. EARLY_MONITOR_*의 잠정 관찰값을 검토하고 격리 환경에서 원본 대조·복구·처리량을 검증한다.
6. 관리자 앱을 검토·재빌드하고 기존 게이트웨이 인증 경로로 확인한다.

AWS 실험에서는 정상 연속 클릭·통신 지연·중복 전송·좌석 경쟁·서버 5xx와 부하 수준을 분리해
오탐·집계 지연·게시 지연을 측정한 뒤 임계값을 재검토한다. 현재 단계는 제재 정책이 아니다.
